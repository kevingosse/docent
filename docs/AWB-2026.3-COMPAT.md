# Assessment — Agent Workbench 2026.3 compatibility

> Written 2026-07-06. Investigation only — no code changed. The goal was to answer *"what does it
> take to make Docent work on both 2026.2 EAP (build 262, current) and 2026.3 (build 263, internal)?"*
> after an internal user reported the plugin doesn't work on 2026.3.
>
> **RESOLVED same day — variant B implemented (see "Resolution" at the bottom).** The body below is
> the original assessment; where later ground truth corrected it, the Resolution section wins
> (notably: `AgentThreadProvider` does **not** keep `.CLAUDE`/`.CODEX` constants, and several 263
> types changed *shape*, not just name — the member-exact mapping lives in `AWB-263-API-MAP.md`,
> which is deliberately kept **outside the repo**, local-only).

## TL;DR

2026.3 **reworks the Agent Workbench API wholesale**: every AWB type the
`awb/` package hard-links moved to the `com.intellij.air.*` namespace **and** was renamed
(`Session` → `Thread`), and both extension
points were renamed. Because the AWB **plugin ID is unchanged** (`com.intellij.agent.workbench`),
Docent's optional `<depends>` still matches on 263, so the gated `docent-awb.xml` module *activates and
then fails* — the renamed EP won't register and the missing classes throw `NoClassDefFoundError`,
tripping the *"Docent can't integrate with the Agent Workbench"* notification. The core review surface
still loads; all workbench integration (session listing, launch-injection, event-push) is dead.

The port itself is mostly mechanical. The one real obstacle to a *single* cross-version binary is the
**launch-injection extension point**, whose name and interface FQN both changed. Recommendation: ship
**two build variants** split by `since/until-build`.

## How this was established

- No 2026.3 Rider/AWB is installed locally (only 2026.1 / 2026.2).
- The `E:\JetBrains\intellij-community` reference checkout is a stale June-17 `263.SNAPSHOT` that
  actually *predates* the 262 migration (it has no `com.intellij.platform.ai.agent` package at all), so
  it is **not** a reliable picture of the current 2026.3.
- Ground truth came from the full Ultimate monorepo at `E:\JetBrains\Ultimate`, `origin/master`
  (`community/build.txt` = `263.SNAPSHOT`, HEAD dated 2026-07-06). All facts below were read from that
  ref with `git grep` / `git show` (no checkout, working tree untouched).

## Ruled out first: the descriptor is not the problem

The generated descriptor (`build/tmp/patchPluginXml/plugin.xml`) emits `since-build="252"` with **no
`until-build`** cap. So 2026.3 does *not* reject the plugin at install/load time — the failure is
entirely inside the gated AWB module, not descriptor gating. (`DocentSeamCheck` doesn't catch it either:
it only verifies the *reflective* chat/editor seams, not the compiled `platform.ai.agent.*` /
`agent.workbench.*` references.)

## The delta (262 → 263)

Two axes changed at once: the package root (`com.intellij.platform.ai.agent.*` **and**
`com.intellij.agent.workbench.*` → `com.intellij.air.*`, across relocated modules) and the domain
vocabulary (`Session` → `Thread`).

| Docent references today (262) | 2026.3 (build 263) |
|---|---|
| `platform.ai.agent.core.session.AgentSessionProvider` | `air.shared.core.thread.AgentThreadProvider` |
| `…core.session.AgentSessionLaunchMode` | `air.shared.core.thread.AgentThreadLaunchMode` |
| `…sessions.core.providers.AgentSessionProviders` | `air.threads.core.providers.AgentThreadProviders` |
| `…providers.AgentSessionTerminalLaunchSpec` | `air.shared.core.thread.AgentThreadTerminalLaunchSpec` |
| `…launch.AgentSessionLaunchContributor` | `air.threads.launch.AgentThreadLaunchContributor` |
| `…launch.McpStreamUrlProvider` | `air.threads.launch.McpStreamUrlProvider` |
| `agent.workbench.prompt.core.AgentPrompt*` | `air.prompt.core.*` (`AgentPromptLauncherBridge`, `AgentPromptModels`, …) |
| `agent.workbench.sessions.state.AgentSessionsStateStore` | `air.threads.runtime.state.AgentThreadsStateStore` |
| `…state.AgentSessionLaunchProfileStateService` | `air.threads.runtime.state.AgentThreadLaunchProfileStateService` |
| `sessions.buildAgentSessionLaunchProfileMenuModel` / `resolve…Items` / `launchProfileActionText` | `air.threads.runtime.buildAgentThreadLaunchProfileMenuModel` / `resolve…Items` / `launchProfileActionText` |
| **EP** `com.intellij.agent.workbench.sessionLaunchContributor` | **EP** `com.intellij.air.threadLaunchContributor` |
| **EP** `com.intellij.agent.workbench.mcpStreamUrlProvider` | **EP** `com.intellij.air.mcpStreamUrlProvider` |

Notes:
- `AgentThreadProvider` is still a value class with `from()` / `.CLAUDE` / `.CODEX` (the value-class shape
  the current code depends on survives).
- The reflective chat seams (`com.intellij.agent.workbench.chat.AgentChatVirtualFile` /
  `AgentChatFileEditor`, `sendText`) were **not** re-verified against 263 in this pass — they likely moved
  under `com.intellij.air.*` too and must be re-checked as part of any fix.

## Why the user sees a failure (exact mechanism)

1. AWB plugin **ID is still `com.intellij.agent.workbench`** on 263 (display name still "Agent Workbench";
   only the code namespace/types were renamed).
2. So Docent's `<depends optional="true" config-file="docent-awb.xml">com.intellij.agent.workbench</depends>`
   still matches → `docent-awb.xml` activates.
3. Its `<sessionLaunchContributor>` `<extensions>` block targets the old EP, which no longer exists →
   registration error.
4. `DocentWorkbenchSetup` (postStartupActivity) instantiates `WorkbenchSessionDirectory` /
   `DocentEventNotifier`, which reference the now-missing `platform.ai.agent.*` / `agent.workbench.*`
   classes → `NoClassDefFoundError`, caught by its `try/catch` → fires the *"Docent can't integrate with
   the Agent Workbench"* notification.
5. Net effect: core review surface works; **all** workbench integration is dead.

## What it takes to fix

The renames are consistent and mechanical — mostly a find-replace of `Session`→`Thread` and the package
roots — so most of `awb/` is a straightforward port. The split is:

- **Portable to a single reflective binary:** session listing / event push / launcher
  (`WorkbenchSessionDirectory`, `DocentEventNotifier`, `WorkbenchAgentLauncher`). They're already
  half-reflective; probing two vocabularies (`AgentSession*` vs `AgentThread*`, two package roots) is
  tedious but doable.
- **The hard part — launch-injection** (`DocentLaunchContributor`): it's wired through a **declarative EP
  whose name *and* interface FQN both changed**, and because the plugin ID is identical on 262 and 263 you
  **cannot** gate a separate `config-file` per version by dependency (both would load). A single compiled
  class can't implement two interfaces that never coexist.

### Options

**A. Single reflective binary.** Make all AWB touchpoints reflective and register the launch contributor
via a JDK dynamic proxy under both EP names. One artifact, survives future renames, but noticeably more
code and fragility — and the launch-injection path is genuinely awkward (exotic proxy + tolerating an
"unknown EP" log on the mismatched build).

**B. Two build variants (recommended).** Keep type-safe compiled references; produce a 262 artifact
(`until-build="262.*"`) and a 263 artifact (`since-build="263"`), each compiling `awb/` against its own
AWB coordinates. The repo/Marketplace serves the right one per IDE build. CI already has the download-mode
plumbing (`riderVersion` / `agentWorkbenchVersion`), so the work is: parameterize the AWB coordinates, add
a 263 source set (or a thin per-version `awb-api` implementation behind a platform-clean facade), and
publish two artifacts.

Because the type *names* differ (`AgentSessionProvider` vs `AgentThreadProvider`), variant B can't be a
pure import-swap of shared source; it needs either two `awb/` source trees or a small compat facade in the
platform-clean core with two implementations.

### Rough effort (variant B)

- ~1 day: mechanical 263 port of `awb/` + the platform-clean facade.
- ~0.5 day: dual-artifact build + CI wiring (two AWB coordinates, two `since/until-build` ranges).
- Plus verification on a real 2026.3 build (re-check the reflective chat seams; confirm the EP registers).

## Follow-ups / open questions

- Re-verify the reflective chat seams (`AgentChatVirtualFile` / `AgentChatFileEditor` / `sendText`) on 263
  — they almost certainly moved to `com.intellij.air.*` and `DocentSeamCheck` must be updated in lockstep.
- Extend `DocentSeamCheck` (or an equivalent) to cover the **compiled** references too, so a future
  package move degrades gracefully instead of throwing at class-load.
- Confirm the exact 263 EP interface method signatures (`AgentThreadLaunchContributor.contribute(...)`)
  and the `AgentThreadTerminalLaunchSpec` field names before porting.
- Decide the internal distribution model (single repo serving both artifacts by build) so variant B's two
  artifacts resolve correctly per IDE.

# Resolution (2026-07-06, plugin 0.5.0)

**Variant B was implemented the same day** — with one crucial clarification that defused the main worry
about it: *two artifacts ≠ two plugins*. Both artifacts share the plugin id `com.kevingosse.docent` and
one Marketplace listing; they differ only in version suffix and build range (`0.5.0-262`, since 252 /
until `262.*` — the previously-open range is now capped — and `0.5.0-263`, since 263 / open). The
Marketplace serves whichever is compatible, and after an IDE upgrade the IDE offers the matching version
of the *same* plugin — users never uninstall/reinstall. This is the JetBrains-documented pattern
(SemVer + `-NNN` suffix per platform branch); the compatibility range of already-published versions is
editable post-upload, so the open-range **0.4.6 should be capped at `262.*`** once on a Marketplace.

**What was built** (details in the code + `build.gradle.kts` narration):

- **Member-exact 262→263 map**: `AWB-263-API-MAP.md`, extracted from the monorepo — supersedes this
  doc's table, and is deliberately kept **outside the repo** (local-only, next to the compile-classpath
  dir). 5 of 7 `awb/` files had *shape* changes beyond renames (new `contribute` param,
  provider constants gone, prompt-launch restructured + `suspend`, chat seam reshaped); the `mcp/` seam
  is byte-for-byte identical on 263 (was unverified here).
- **Source layout**: AWB-free logic (incl. all command-line injection surgery, now in
  `awb/LaunchInjection.kt`) is shared in `src/main`; the AWB-touching remainder exists per-variant in
  `src/awb262` / `src/awb263` under identical package+class names; `-PawbTarget=262|263` (default 262)
  selects the tree, descriptor variant (`docent-awb.xml` with the old vs `com.intellij.air` EP),
  coordinates, version suffix and build range.
- **CI/release**: `build-262` stays the blocking job; the 263 legs (build + release) are gated on the
  repo variable `AWB263_MARKETPLACE_VERSION` — skipped silently until AWB 263 publishes (no public
  channel has it as of 2026-07-06; the Rider `2026.3-SNAPSHOT` base *is* publicly resolvable), then
  activated by setting the variable, no commit needed.
- **263 compile verification without any published AWB 263**: a 263 AWB plugin was compiled from
  monorepo source (Bazel; minutes, since the shared build cache serves prebuilt outputs) and assembled
  into a plugin-shaped dir (`lib/` + `lib/modules/`) consumed via `-PagentWorkbenchPluginPath263`.
  `code-review-docent-0.5.0-263.zip` builds green; **zero compile fixes** were needed against the API
  map. NB: such a dir is a *compile classpath*, not an installable plugin (the official distribution
  repacks and bundles third-party libs).

**Field observation that reframed the user report**: on an early Rider 2026.3 (263.1142, Toolbox), AWB
262.8377 is rejected as incompatible at load, so `docent-awb.xml` never activates — Docent runs
core-only with *no* error balloon ("works fine", minus workbench integration, and the IDE's Marketplace
query for a 263-compatible AWB 404s). The hard failure only appears with a pairing where a 263 AWB
actually loads.

**Runtime verification (same day)**: with a 263 AWB installed from CI on a real 2026.3, the 0.4.6
artifact reproduces exactly the assessed failure (`NoClassDefFoundError: …AgentSessionProvider` balloon),
and **0.5.0-263 works**. That also settles the two seams the API map had marked UNVERIFIED-in-principle:
registration into `com.intellij.air.threadLaunchContributor` succeeds despite the owning module's
`visibility="internal"`, at least on this build.

**Still open:**
- Exercise the reflective editor→terminal-tab traversal on 263 in anger (`AgentThreadViewFileEditor`
  lost `tab`; the 263 code does a best-effort walk that degrades to the seam-check warning) — a full
  live review on a 263 IDE is the real test.
- `verifyPlugin` for the 263 target is a deliberate no-op until a public 263 IDE build exists.
- The 263 API was frozen from monorepo master @ `1cfd91b5525d4` (2026-07-06); re-verify once a real
  263 EAP/AWB build ships, then pin `agentWorkbenchVersion263`/`riderVersion263` in lockstep as usual.

## Update (2026-07-06, later) — dual variants collapsed into ONE artifact

The dual-variant design above was overtaken by events the same day. Rider **2026.2 EAP9** (build
**262.8665**, AWB `262.8665.20260706`) shipped the `air.*` rename **into the 262 line itself** — so the
262 EAP8→EAP9 bump (262.8377 → 262.8665) *broke* the shipped `0.5.x-262` artifact with the exact
`NoClassDefFoundError: …AgentSessionProvider` this doc assessed for 263 (seen in a user's `idea.log`;
the plugin dir is now `air-plugin`, all modules `intellij.air.*`).

Decisive facts, both verified 2026-07-06:
1. **The air.* API is byte-identical across 262.8665 and 263.1174** — `javap -public` diff of all 14
   `air.*` types the seam references: no signature drift.
2. **No AWB 263 exists on any public channel** (Marketplace newest = `262.8665.20260706`; no `263.*`),
   so CI cannot download a dependency to build a *native* 263 artifact at all.

Together these mean a **single** binary compiled against the `air.*` API is both sufficient and the
*only* CI-viable way to cover 2026.3. So the `awb262`/`awb263` twin trees were merged into `src/awb`,
`awbTarget` and all `*263` gradle knobs were removed, and the plugin now builds as **one artifact** with
`since-build 262.8665` / `until-build 263.*`. It loads on 2026.2 EAP9+ and all of 2026.3. CI base is
`riderVersion 2026.2-EAP9-SNAPSHOT` + `agentWorkbenchVersion 262.8665.20260706` (both confirmed
resolvable from the snapshots repo / Marketplace). Early-262 EAPs (< 262.8665, old
`platform.ai.agent.*` API) are intentionally dropped. Revisit only if a future build (264+) reworks the
API again — then the range cap and possibly the twin-variant machinery come back.

## Update (2026-07-10, plugin 0.6.0) — the 263 line diverged again (AWB 263.1445, provider→agent rework)

The "byte-identical" fact above held only up to AWB **263.1174**. AWB **263.1445** (IDEA 2026.3 dev
line) reworked the provider model *within* the `air.*` namespace, and 0.5.2 broke on it — this time
worse than a dead seam: our stale `threadLaunchContributor` registration made **every AWB thread launch
fail** with

```
java.lang.AbstractMethodError: … does not define … 'contribute-WeWHIlw(String, String, String, String,
com.intellij.air.shared.core.thread.AgentThreadLaunchSpec, Continuation)' of interface
com.intellij.air.threads.launch.AgentThreadLaunchContributor
```

The delta (established by javap-diffing the installed 262.8665 `air-plugin` against a downloaded
263.1445 one, plus compiling `src/awb` against the 263.1445 classpath to enumerate every break):

| 262.8665..263.1174 | 263.1445+ |
|---|---|
| `AgentThreadTerminalLaunchSpec` | renamed `AgentThreadLaunchSpec` (fields identical, now serializable) |
| `provider: AgentThreadProvider` (value class) | `agentId: AgentId` (value class, same "claude"/"codex" values) |
| `AgentThreadLaunchContributor.contribute-QyV-CsE(…)` | `contribute-WeWHIlw(…)` — both value-class changes feed Kotlin's name mangling |
| `AgentThread.provider` (`getProvider-wYjB3lY`) | `AgentThread.agentId` (`getAgentId-f6jNaPk`) |
| vfile `getProvider(): AgentThreadProvider?` | vfile `getAgentId-…(): String` (and an unrelated `getProviderContentConfig()` landmine for prefix-reflection) |
| `AgentThreadProviders` / `AgentThreadProviderDescriptor` registry | **deleted** → EP-backed `agents.AgentRegistry` / `AgentDescriptor` / `AgentPresentation` |
| `resolveAgentThreadLaunchProfileItems(menuModel, profiles)` in `com.intellij.air.threads` | moved to `air.threads.launch`, new params + item type |
| `McpStreamUrlProvider`, all `air.prompt.core.*` launch types, `AgentThreadsStateStore` shape | **unchanged** (verified by compile + javap) |

**Resolution — still ONE artifact** (no Marketplace AWB 263 exists as of 2026-07-10, so the CI
constraint from the previous section still rules out a native 263 build):

- **Launch injection**: `DocentLaunchContributor` now carries **both interface generations in one
  class**. The 262 shape stays the real compile-time `override`; the 263.1445 shape is a hand-mangled
  backtick-named twin (`` `contribute-WeWHIlw` ``) whose descriptor references a **compile-only stub**
  of `AgentThreadLaunchSpec` (`src/awbStub`, never shipped — the FQN resolves to the real class at
  runtime) and whose spec access is reflective. Works because the JVM resolves interface methods by
  name+descriptor at invoke time and never requires a class to implement all abstract methods at load.
- **Session listing / event push**: the per-thread and per-vfile provider getters are read reflectively
  by mangle-prefix (`getProvider-*` / `getAgentId*`), provider icons go through the new
  version-adaptive `AwbAgentIcons` (static 262 registry, reflective 263 `AgentsKt.AGENT_EP`).
- **Launch-profile menu**: on 263.1445+ the 262-compiled pipeline dies on classloading and the picker
  **degrades to plain "New Claude/Codex session" options** (launching still works via the unchanged
  `AgentPromptLaunchers` bridge). Re-porting the profile menu onto `AgentRegistry`/`AgentMenuModel` is a
  known follow-up.
- **Tripwire**: `DocentSeamCheck` now also verifies the `contribute` mangle is one of the two known
  generations, so a THIRD signature change notifies loudly instead of failing every launch again.

## Update (2026-08-03, plugin 0.7.0) — the layering rework (AWB 262.8665.20260723): generation-spanning ends

Rider **2026.2.0.1** (the release, build `262.8665.385`) ships with AWB **`262.8665.20260723`** — same
`since-build`, so the Marketplace pushed it as a routine update onto machines running 0.6.4, which was
compiled against `262.8665.20260706`. That build **re-layered the whole namespace**: the flat
`com.intellij.air.threads.*` / `air.prompt.core.*` packages were split into `air.backend.*` /
`air.frontend.*` / `air.shared.*`, and the 263.1445 provider→agent rework (above) is folded in — there is
no `AgentThreadProvider` / `AgentThreadTerminalLaunchSpec` anywhere anymore.

Symptom, from a user's Rider (and `idea.log`, since 2026-07-30): the seam-check balloon *"Docent may not
reach Agent Workbench sessions… AgentThreadLaunchContributor is gone… AgentThreadViewTerminalTab is
gone"*. Only 2 of the 5 probes fired because the thread-view vfile/editor package didn't move — but the
real damage was wider: launch injection (the EP implementation can't even load: missing superinterface),
the terminal push, the launcher push, "start a new agent session", and the agent icons.

The delta (javap over the installed `air-plugin/lib/**.jar`, then compiling `src/awb` against it):

| 0.6.4 referenced | AWB 262.8665.20260723 |
|---|---|
| `air.threads.launch.AgentThreadLaunchContributor` | `air.backend.session.launch.AgentThreadLaunchContributor` — **same `contribute-WeWHIlw`** |
| `air.threads.launch.McpStreamUrlProvider` | `air.backend.session.launch.McpStreamUrlProvider` (`Companion.resolve()` unchanged) |
| `air.thread.tui.frontend.AgentThreadViewTerminalTab` | `air.frontend.session.view.tui.AgentThreadViewTerminalTab` (`sendText(3)` unchanged) |
| `air.prompt.core.AgentPrompt{LaunchRequest,LaunchProfile,InitialMessageRequest}` | `air.shared.prompt.*` (same fields; profile's `providerId` deprecated in favour of `agentId`/`effectiveAgentId`) |
| `air.prompt.core.AgentPromptLaunchers` (bridge lookup) | **gone** → `air.shared.prompt.AgentPromptBackendApi.getInstance().launchPrompt(request)` (its frontend wrapper `air.prompt.ui.AgentPromptBackendLaunchClient` is Kotlin-`internal`) |
| `air.threads.core.providers.AgentThreadProviders` (+ the 0.6.x reflective `agents.AgentsKt.AGENT_EP` path) | frontend catalog: `air.frontend.core.agentCatalogSnapshot().agents` → `AgentDescriptorDto.presentation.iconId` (`IconId.icon()`) |
| `air.threads.state.AgentThreadLaunchProfileStateService` | `air.frontend.launch.AgentThreadLaunchProfileStateService` |
| `air.threads.buildAgentThreadLaunchProfileMenuModel` + `resolveAgentThreadLaunchProfileItems` | `air.prompt.ui.buildEnabledAgentCatalogMenuModel` + `air.frontend.launch.buildBuiltInLaunchProfiles` + `air.frontend.launch.resolveAgentThreadLaunchProfileItems` (`air.threads.launchProfileActionText` / `quickStartLabel` still public) |
| `air.thread.view.AgentThreadViewVirtualFile` / `…FileEditor`, `air.threads.state.AgentThreadsStateStore`, `air.shared.core.thread.AgentThread`, EP name `com.intellij.air.threadLaunchContributor` | **unchanged** |

**Resolution — clean retarget, one generation.** Spanning generations is no longer possible for the
launch EP: a JVM class cannot implement a superinterface that doesn't exist, so the 0.6.x trick (one class,
two mangled `contribute`s under a stable interface FQN) has no equivalent for a *moved* interface. So
0.7.0 targets the 20260723 layout only:

- `DocentLaunchContributor` has a single real `override contribute(projectPath, projectDirectory,
  agentId: AgentId, threadId, launchSpec: AgentThreadLaunchSpec)`; the hand-mangled twin, the
  `SpecReflect` helper and the whole `src/awbStub` compile-only source set are **deleted** (kotlinc emits
  the same `contribute-WeWHIlw` descriptor the interface declares — verified with javap on the built jar).
- Pushes and new sessions go through the public RPC surface `AgentPromptBackendApi` (both `getInstance()`
  and `launchPrompt()` are `suspend`, bridged with `runBlockingCancellable` as before).
- The launch-profile picker is **re-ported, not degraded**: enabled agents from the frontend catalog
  snapshot → `buildEnabledAgentCatalogMenuModel` → `buildBuiltInLaunchProfiles` + the user's profiles /
  hidden ids / ordering from `AgentThreadLaunchProfileStateService` → `resolveAgentThreadLaunchProfileItems`.
  Custom launch profiles show up again.
- Session listing and the store now read `AgentThread.agentId` / vfile `agentId` **statically** (the
  mangle-prefix reflection existed only to span generations).
- The editor→terminal walk is now **verified, not guessed** (it was UNVERIFIED since 0.5.0) and extracted
  into one place, `AwbTerminalTab`: `AgentThreadViewFileEditor` (Kotlin-`internal`, so matched by FQN) holds
  the content in `activeContent`/`mountedContent`, and `AgentThreadViewTerminalContent.terminalTab` holds
  the `AgentThreadViewTerminalTab`. A field-name change is absorbed by a type-driven fallback scan.
- `DocentSeamCheck` probes the new FQNs, the exact `contribute-WeWHIlw` name, the prompt-launch API, and
  the editor's content fields.

**Consequence to accept:** this artifact's seam matches AWB `262.8665.20260723`+ only. On an IDE carrying
an older air.* workbench (incl. 263.1174 / 263.1445) the core review surface still loads and works, while
the workbench seam reports itself broken through the seam-check balloon. Since AWB pins itself to a single
IDE build (`until-build 262.8665.*` for this one), chasing the installed workbench is the normal state of
affairs here — re-javap the installed jars whenever it updates.

## Update (2026-08-03, plugin 0.7.1) — release-line vs nightly AWB; retarget to 262.8665.28

0.7.0 was retargeted to the AWB build that happened to be installed, `262.8665.20260723`. That build turned out
to be a **nightly** (date-stamped trailer), built against the platform *of that day* — and it is not viable on a
released Rider. When Rider updated `262.8665.328` → **`262.8665.385`** (2026.2 → 2026.2.0.1), that nightly
started failing every agent thread tab:

```
java.lang.NoClassDefFoundError: com/intellij/terminal/frontend/session/TransferableTerminalSessionFactory
	at …tui.ToolWindowAgentThreadViewTerminalTabs.prepareTab(AgentThreadViewTerminalTabSupport.kt:258)
```

`.385` deleted that platform class (the package now holds `TerminalSessionsManager` / `TerminalSessionStartKt`),
so `reportTerminalInitializationFailure` closed each tab as it opened. A second, milder symptom on the same
pairing: `intellij.air.backend.acp.runtime` was excluded because it depends on `intellij.platform.ide.impl.wsl`,
which the platform registers `internal` to namespace `jetbrains` while AWB's content namespace is
`agent-workbench` — that cascades to `acp`, `acp.debug`, `acp.codex`, `acp.mcp`. (The platform has an escape
hatch for that class of mismatch: `-Dintellij.platform.plugin.modules.check.visibility=warning|disabled`,
default `error` — see `PluginSetBuilder.checkVisibilityAndReturnErrorMessage`.)

**The release-line AWB build `262.8665.28` fixes both** (verified by inspecting the published zips): it vendors
its own `AirTransferableTerminalSessionFactory` instead of calling the deleted platform class, and its
`acp.runtime` module dropped the `wsl` dependency. A sweep of every `com.intellij.terminal.*` /
`org.jetbrains.plugins.terminal.*` class it references against all 372 821 classes in the Rider install found
nothing missing. **Rule going forward: pin `agentWorkbenchVersion` to a release-line build (`262.8665.28`), not
a date-stamped nightly.** NB the Marketplace won't offer `.28` as an *update* over `…20260723` (version
comparison puts `28` below `20260723`), so switching means uninstall + reinstall, or install-from-disk with the
**zip** (installing the bare `air-plugin.jar` out of an unpacked zip leaves the plugin without its
`lib/modules/*` content modules and fails with `ClassNotFoundException: …AgentRemoteSettingInfoProvider`).

`.28` shares 0.7.0's layered namespace and the identical `contribute-WeWHIlw` launch EP, but its prompt/catalog
surface differs — the delta 0.7.1 absorbs:

| 262.8665.20260723 (nightly) | 262.8665.28 (release line) |
|---|---|
| `AgentPromptInitialMessageRequest(prompt, projectPath, …)` | `(prompt, renderedContextEnvelope, agentOptionIds)` — **no `projectPath`** (an arity change: silent `NoSuchMethodError`, not a compile error) |

## 2026-09-08 update — 0.8.0: Air 263.4739 (bundled in IDEA 2026.3): plugin-id rename + the ACP fold

> Diagnosed against IntelliJ IDEA 2026.3 build 263.4739 with its **bundled** `air-plugin` 263.4739.0 (Air is now
> shipped inside the IDE; the 263.1445 copy in the Roaming plugins dir was out of range and disabled), source of
> truth `E:\JetBrains\Ultimate\plugins\air` at HEAD 66ab822545a6c (2026-09-04).

Symptom: a Claude session launched from Air never saw the `docent` MCP server, and idea.log had **zero**
`docent.awb` lines — not even the seam-check balloon. Two independent breaks:

**1. The plugin id changed.** Commit `2a5e9209b067f` (2026-07-28, "[air] Migrate plugin id to com.intellij.air")
renamed `com.intellij.agent.workbench` → `com.intellij.air` with no `pluginAlias`. The Docent's

loaded: no launch contributor, no seam check, no session directory. (The build's Marketplace coordinate used the
old id too.) Fix: depend on `com.intellij.air`; compile against the IDE's bundled plugin
(`bundledPlugin("com.intellij.air")`) — there is no separate Marketplace artifact for the bundled 263 line.

**2. Claude/Codex became "folded" ACP agents.** `shared/session/src/FoldedAcpAgents.kt`
(`acp.registry.claude-acp → claude`, `acp.registry.codex-acp → codex`, centralized 2026-08-21) routes the default
Chat surface through the ACP adapters. For those launches `buildBaseLaunchSpec` returns
`structuredNewSessionLaunchSpec()` / `structuredResumeSessionLaunchSpec()` — **`command = emptyList()`**. The
`threadLaunchContributor` EP still exists and still fires (same `air.backend.session.launch` FQN, same

translating the ACP `session/new` `mcpServers` array, which Air fills from its own EP. The Terminal surface (CLI in
a terminal tab, Full Access presets, `preferTerminalSurface`) still exists and still takes CLI args.

The ACP-side seams Air 263.4739 offers (all `@Internal`; the `ai-code-review` and `llm` plugins register on them
from outside the Air plugin, so third-party registration is a supported pattern):

Why the supplement and not a system prompt: `claude-acp` 0.75.1 *would* accept `_meta.systemPrompt` on
`session/new` (string or `{append: …}` preset options), but Air's `buildAcpSessionMeta` only ever sends
`additionalRoots`, and no EP adds to `_meta`. The supplement is appended to the delivered text of every outgoing
turn (a new session's first turn included), wire-only — the transcript never shows it. `applied()` is the hook
that fires as the payload goes out, so that's where the thread is marked as introduced (the docs forbid mutating
state in `supplement()`). The context carries `threadId`, `projectPath`, `deliveredText`, `attachments` — **no
agent id** — so `DocentAcpMcpServerProvider` (which sees `AcpAgentId.rawId` = `claude-acp` / `codex-acp`) records
thread → provider, with `AgentThreadsStateStore` as the fallback for a thread it didn't see created.

Identity: `SessionRef.threadId` == the supplement context's `threadId` == `AgentThreadViewVirtualFile.threadId`
== the `AgentThread.id` in the store == `AgentPromptLaunchRequest.targetThreadId` — i.e. the same sessionToken
the terminal path bakes in, so `docent_finalize_trail(sessionToken)` and the `AgentPromptBackendApi` push work
unchanged for ACP threads. The live-terminal push channel (`AwbTerminalTab.sendText`) has no terminal to type
into on ACP and falls through to the launch-client push, as designed.
